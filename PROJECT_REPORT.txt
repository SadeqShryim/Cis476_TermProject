## 1. Project Overview

**DriveShare** is a peer-to-peer car rental platform inspired by Turo.com. The application allows car owners to list their vehicles for rent and renters to search, book, and pay for rentals. The system implements six design patterns and features a React frontend with a Python/FastAPI backend using SQLite for persistence.

### Key Features
- User registration and authentication with SHA-256 password hashing
- Security questions for password recovery (Chain of Responsibility pattern)
- Car listing management with Builder pattern
- Search and booking with overlap prevention
- Watch system for price drop notifications (Observer pattern)
- In-app messaging between users
- Simulated payment processing (Proxy pattern)
- Session management (Singleton pattern)
- UI component coordination (Mediator pattern)

### 2.2 Design Patterns

#### 2.2.1 Singleton Pattern — Session Management

```plantuml
@startuml singleton_pattern
title Singleton Pattern — Session Management

skinparam classAttributeIconSize 0
skinparam packageStyle rectangle

package "patterns.singleton" {
  class SessionManager <<Singleton>> {
    {static} - _instance : SessionManager
    - _current_user : dict
    --
    + {static} __new__(cls)
    + login(user)
    + logout()
    + get_current_user() : dict
    + is_authenticated() : bool
    + update_user(updates)
    + refresh()
    + {static} reset()
  }
}

package "services.auth_service" {
  class "login() / logout() / ..." as auth_svc <<Client>>
}

package "api.routes.auth" {
  class "login / logout endpoints" as api_auth <<Client>>
}

SessionManager <.. auth_svc : **SessionManager()**
SessionManager <.. api_auth : **SessionManager()**

note right of SessionManager
  **Pattern Role Mapping**
  **Singleton** → **SessionManager**
  --
  **__new__** ensures only one instance exists.
  All callers receive the same **_instance**.
  Tracks **_current_user** across the entire application.
  --
  **reset()** clears the singleton (used for testing).
end note

@enduml
```

**Description:** The Singleton pattern ensures only one `SessionManager` instance exists throughout the application lifecycle. This is critical for maintaining consistent user session state across all components. The `__new__` method intercepts object creation and returns the existing instance if one already exists. Key operations include `login()` to set the current user, `logout()` to clear the session, and `refresh()` to reload user data from storage (useful after balance changes from payments).

#### 2.2.2 Observer Pattern — Car Watch System

```plantuml
@startuml observer_pattern
title Observer Pattern — Car Watch System

skinparam classAttributeIconSize 0
skinparam packageStyle rectangle

package "patterns.observer" {
  class CarSubject <<Subject>> {
    - _observers : List
    + attach(observer)
    + detach(observer)
    + detach_by_user(user_id)
    + notify(car_data, change_type)
  }

  class WatcherObserver <<Observer>> {
    + user_id : string
    + max_price : float
    + desired_start : string
    + desired_end : string
    + callback : function
    + update(car_data, change_type)
  }

  class WatchManager {
    - _subjects : Map<car_id, CarSubject>
    + get_or_create_subject(car_id)
    + add_watcher(car_id, observer)
    + remove_watcher(car_id, user_id)
    + notify_car_change(car_id, car_data, change_type)
  }
}

package "services" {
  class "car_service" as car_service_mod {
    .. global ..
    **watch_manager** : WatchManager
    --
    + update_listing(...)
  }

  class "watch_service" as watch_service_mod {
    + watch_car(user_id, car_id, ...)
    + unwatch_car(...)
    + restore_watchers()
  }
}

package "services.notification_service" {
  class "add_notification(...)" as add_notif <<callback target>>
}

WatchManager "1" o-- "0..*" CarSubject : manages
CarSubject "1" o-- "0..*" WatcherObserver : notifies

watch_service_mod ..> WatcherObserver : **creates**
WatcherObserver ..> add_notif : **callback**

note right of CarSubject
  **Pattern Role Mapping**
  **Subject** → **CarSubject**
  **Observer** → **WatcherObserver**
  --
  When a car's price drops or availability
  changes, all watchers are notified via
  their registered callback function.
end note

@enduml
```

**Description:** The Observer pattern implements the "Watch" feature where renters can subscribe to car listings and receive notifications when prices drop or availability changes. Each `CarSubject` maintains a list of `WatcherObserver` instances. When `car_service.update_listing()` detects a price drop, it calls `WatchManager.notify_car_change()`, which triggers the `update()` method on all observers. Each observer evaluates the change against their criteria (e.g., `max_price`) and uses a callback to create a notification if the criteria are met.

#### 2.2.3 Builder Pattern — Car Listing Construction

```plantuml
@startuml builder_pattern
title Builder Pattern — Car Listing Construction

skinparam classAttributeIconSize 0
skinparam packageStyle rectangle

package "patterns.builder" {
  class CarListingBuilder <<Builder>> {
    - _owner_id : string
    - _make : string
    - _model : string
    - _year : int
    - _mileage : int
    - _daily_price : float
    - _location : string
    - _features : List[string]
    - _availability : List[dict]
    --
    + reset() : self
    + set_owner(owner_id) : self
    + set_make(make) : self
    + set_model(model) : self
    + set_year(year) : self
    + set_mileage(mileage) : self
    + set_daily_price(price) : self
    + set_location(location) : self
    + add_feature(feature) : self
    + add_availability(start, end) : self
    + validate() : bool
    + build() : dict
  }
}

package "models.car" {
  class "create_car(...)" as create_car <<Product Factory>> {
    returns car listing **dict**
  }
}

package "api.routes.cars" {
  class "POST /cars" as create_route <<Director>> {
    instantiates CarListingBuilder
    fluent method calls
    build()
  }
}

package "services.car_service" {
  class "create_listing(car_data)" as car_create_svc {
    persists dict to database
  }
}

CarListingBuilder ..> create_car : **build()** calls
create_route ..> CarListingBuilder : **uses**
create_route ..> car_create_svc : **create_listing**

note right of CarListingBuilder
  **Pattern Role Mapping**
  **Builder** → **CarListingBuilder**
  **Product** → car listing **dict**
  **Director** → API route handler
  --
  Fluent interface: each setter returns **self**.
  **validate()** ensures required fields are set.
  **build()** calls **create_car()** to produce final dict.
end note

@enduml
```

**Description:** The Builder pattern provides a step-by-step, fluent interface for constructing complex car listing objects. This is beneficial because car listings have many optional fields (features, availability windows) and required fields (make, model, year, price, location). The `CarListingBuilder` accumulates field values through chained setter calls, validates that all required fields are present via `validate()`, and finally produces the car dictionary via `build()`. The API route acts as the "Director" that orchestrates the build process based on user input.

#### 2.2.4 Proxy Pattern — Payment Processing

```plantuml
@startuml proxy_pattern
title Proxy Pattern — Payment Processing

skinparam classAttributeIconSize 0
skinparam packageStyle rectangle

package "patterns.proxy" {
  class RealPaymentService <<RealSubject>> {
    + process(renter_id, owner_id, amount) : dict
  }

  class PaymentProxy <<Proxy>> {
    - _real_service : RealPaymentService
    - _transaction_log : List[dict]
    --
    + process_payment(renter_id, owner_id, amount, booking_id?) : dict
    + get_transaction_log() : List[dict]
    - _log_transaction(...)
  }
}

package "services.payment_service" {
  class "process_payment(...)" as pay_svc <<Client API>> {
    delegates to **PaymentProxy**
  }
}

package "storage.db_store" {
  class "update(...)" as db_update {
    updates user balances
  }
}

PaymentProxy o-- RealPaymentService : delegates
pay_svc ..> PaymentProxy : **process_payment()**
RealPaymentService ..> db_update : modifies balances

note right of PaymentProxy
  **Pattern Role Mapping**
  **RealSubject** → **RealPaymentService**
  **Proxy** → **PaymentProxy**
  --
  **Proxy responsibilities**:
  1. Validate payment amount (> 0)
  2. Validate renter has sufficient balance
  3. Log transaction attempt
  4. Delegate to **RealPaymentService**
  5. Log transaction result
  6. Create notifications for both parties
  7. Mark booking as paid
end note

@enduml
```

**Description:** The Proxy pattern adds validation, logging, and notification layers around the payment processing logic. The `PaymentProxy` acts as a gatekeeper: it first validates that the payment amount is positive and that the renter has sufficient balance. If validation passes, it delegates to `RealPaymentService.process()` which performs the actual balance transfers. The proxy then logs the transaction (success or failure), creates notifications for both renter and owner, and marks the associated booking as paid. This separation of concerns keeps the core payment logic simple while adding cross-cutting concerns transparently.

#### 2.2.5 Chain of Responsibility Pattern — Password Recovery

```plantuml
@startuml chain_of_responsibility_pattern
title Chain of Responsibility Pattern — Password Recovery

skinparam classAttributeIconSize 0
skinparam packageStyle rectangle

package "patterns.chain_of_responsibility" {
  class SecurityQuestionHandler <<Handler>> {
    - _question_index : int
    - _next_handler : SecurityQuestionHandler
    --
    + set_next(handler) : Handler
    + handle(user, answers) : bool
  }

  class "build_security_chain()" as build_chain <<Factory Function>> {
    returns first handler in chain
  }
}

package "services.auth_service" {
  class "recover_password(...)" as recover_pw <<Client>> {
    uses build_security_chain()
    calls chain.handle(user, answers)
  }
}

SecurityQuestionHandler "1" --> "0..1" SecurityQuestionHandler : _next_handler

build_chain ..> SecurityQuestionHandler : **chains**\nhandler[0] → handler[1] → handler[2]
recover_pw ..> build_chain : **calls**

note bottom of SecurityQuestionHandler
  **Pattern Role Mapping**
  **Handler** → **SecurityQuestionHandler**
  **Client** → **auth_service.recover_password**
  --
  Chain of 3 handlers, one per security question.
  Each handler verifies one answer.
  If answer matches → pass to next handler.
  If answer fails → return False (chain stops).
  If all pass → password reset allowed.
end note

@enduml
```

**Description:** The Chain of Responsibility pattern implements the multi-step password recovery process. Each `SecurityQuestionHandler` is responsible for verifying one of the user's three security question answers. The handlers are linked via `set_next()` to form a chain. When `handle()` is called, the first handler checks if the first answer is correct. If so, it passes control to the next handler; if not, it returns `False` immediately. This continues until all three answers are verified (returns `True`) or any answer fails (returns `False`). The factory function `build_security_chain()` constructs the chain with handlers for indices 0, 1, and 2.

#### 2.2.6 Mediator Pattern — UI Component Communication

```plantuml
@startuml mediator_pattern
title Mediator Pattern — UI Component Communication

skinparam classAttributeIconSize 0
skinparam packageStyle rectangle

package "frontend/src/patterns/mediator.js" {
  class Colleague <<abstract>> {
    # name : string
    # mediator : DriveShareMediator
    + send(event, data)
    + receive(event, data)
  }

  class DriveShareMediator <<ConcreteMediator>> {
    - _colleagues : Map<name, Colleague>
    - _eventLog : List
    --
    + register(colleague)
    + unregister(name)
    + notify(senderName, event, data)
    + getEventLog()
  }
}

package "frontend/src/hooks/useColleague.js" {
  class ComponentColleague <<ConcreteColleague>> {
    - _handler : function
    + receive(event, data)
  }
}

package "frontend/src/context/MediatorContext.jsx" {
  class "MediatorProvider" as MediatorCtx {
    provides mediator to React tree
  }
}

Colleague <|-- ComponentColleague
ComponentColleague --> DriveShareMediator : mediator.notify(...)
DriveShareMediator ..> Colleague : routes to receive()
MediatorCtx ..> DriveShareMediator : provides singleton

note right of DriveShareMediator
  **Event Types:**
  - USER_LOGGED_OUT
  - CAR_LISTED, CAR_UPDATED, CAR_DELETED
  - BOOKING_CREATED, BOOKING_CANCELLED, BOOKING_PAID
  - CAR_WATCHED, CAR_UNWATCHED
  - MESSAGE_SENT, NOTIFICATION_RECEIVED
  - REVIEW_SUBMITTED
  
  **Registered Colleagues:**
  NotificationBell, BalanceDisplay, CarList,
  WatchList, BookingList, ConversationList,
  MyCarsOwnerList, PaymentButton, BookingModal,
  CarForm, ChatWindow, ReviewForm
end note

@enduml
```

**Description:** The Mediator pattern decouples React UI components by centralizing their communication through `DriveShareMediator`. Instead of components directly calling each other, they register as "colleagues" with the mediator and communicate via events. For example, when `PaymentButton` processes a payment, it sends a `BOOKING_PAID` event. The mediator routes this to `BalanceDisplay` (to refresh the balance), `BookingList` (to update payment status), and `NotificationBell` (to show a new notification). This pattern eliminates tight coupling between components and makes the event flow explicit and traceable via `getEventLog()`.

### 3.2 Table Descriptions

#### **users**
Stores user account information including authentication credentials and financial balance.

| Column | Type | Description |
|--------|------|-------------|
| id | VARCHAR(36) | Primary key (UUID) |
| email | VARCHAR | User's email address (indexed for login lookup) |
| password_hash | VARCHAR | SHA-256 hash of the password |
| security_questions | JSON | Array of 3 objects with `question` and `answer` fields |
| balance | FLOAT | User's wallet balance (starts at $1000) |
| created_at | VARCHAR | ISO timestamp of account creation |

#### **cars**
Stores vehicle listings posted by owners.

| Column | Type | Description |
|--------|------|-------------|
| id | VARCHAR(36) | Primary key (UUID) |
| owner_id | VARCHAR(36) | Foreign key to users table |
| make | VARCHAR | Manufacturer (e.g., "Toyota") |
| model | VARCHAR | Model name (e.g., "Camry") |
| year | INTEGER | Model year |
| mileage | INTEGER | Current odometer reading |
| daily_price | FLOAT | Rental price per day |
| location | VARCHAR | Pick-up location |
| features | JSON | Array of feature strings (e.g., ["Bluetooth", "GPS"]) |
| availability | JSON | Array of `{start, end}` date windows |
| watchers | JSON | Array of user IDs watching this car |
| is_active | BOOLEAN | Soft-delete flag (false = deleted) |
| created_at | VARCHAR | ISO timestamp of listing creation |

#### **bookings**
Stores rental reservations between renters and owners.

| Column | Type | Description |
|--------|------|-------------|
| id | VARCHAR(36) | Primary key (UUID) |
| car_id | VARCHAR(36) | Foreign key to cars table |
| renter_id | VARCHAR(36) | Foreign key to users (person renting) |
| owner_id | VARCHAR(36) | Foreign key to users (car owner) |
| start_date | VARCHAR | Rental start date (YYYY-MM-DD) |
| end_date | VARCHAR | Rental end date (YYYY-MM-DD) |
| total_price | FLOAT | Calculated total (daily_price × days) |
| status | VARCHAR | "confirmed" or "cancelled" |
| paid | BOOLEAN | Payment completion flag |
| created_at | VARCHAR | ISO timestamp of booking creation |

#### **messages**
Stores direct messages between users.

| Column | Type | Description |
|--------|------|-------------|
| id | VARCHAR(36) | Primary key (UUID) |
| sender_id | VARCHAR(36) | Foreign key to users (message author) |
| receiver_id | VARCHAR(36) | Foreign key to users (recipient) |
| content | VARCHAR | Message text content |
| read | BOOLEAN | Read receipt flag |
| timestamp | VARCHAR | ISO timestamp of when message was sent |

#### **notifications**
Stores system-generated notifications for users.

| Column | Type | Description |
|--------|------|-------------|
| id | VARCHAR(36) | Primary key (UUID) |
| user_id | VARCHAR(36) | Foreign key to users (notification recipient) |
| content | VARCHAR | Notification message text |
| type | VARCHAR | Category: "general", "booking", "payment", "watch", or "message" |
| read | BOOLEAN | Dismissal flag |
| timestamp | VARCHAR | ISO timestamp of notification creation |

#### **reviews**
Stores post-rental reviews between renters and owners.

| Column | Type | Description |
|--------|------|-------------|
| id | VARCHAR(36) | Primary key (UUID) |
| booking_id | VARCHAR(36) | Foreign key to bookings table |
| reviewer_id | VARCHAR(36) | Foreign key to users (person writing review) |
| reviewed_id | VARCHAR(36) | Foreign key to users (person being reviewed) |
| reviewed_role | VARCHAR | "owner" or "renter" |
| rating | INTEGER | Score from 1-5 |
| comment | VARCHAR | Review text |
| created_at | VARCHAR | ISO timestamp of review submission |
